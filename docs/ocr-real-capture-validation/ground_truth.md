## 이미지 2 / 이미지 3: 통합탭 (얼굴람스 / 팔뚝람스)

통합탭은 블로그탭과 구조가 근본적으로 다르다. 순수 블로그 글 목록이 아니라, 서로 다른
성격의 "모듈"이 섞여 나온다. 스펙 7절이 말하는 "모듈과 일반 게시글 구분"이 실제로
얼마나 복잡한지 보여주는 좋은 사례다. 두 이미지 모두 공통 구조:

1. **AI 브리핑** — 게시물이 아닌 AI 요약 모듈(썸네일 카로셀 + 요약문 + "펼쳐서 더보기").
   앱 관점에서는 "게시물을 포함하지 않는 모듈"(is_post_bearing=false)로 분류되어야 정상.
2. **"무엇이든 물어보세요" 입력창** — 게시물 아님, 완전히 무시되어야 함.
3. **카페 글 2~3건** — 채널명에 카페 이름 + "[대표]" 배지 + 상대 날짜. 제목 아래 본문
   미리보기, 그 아래 "RE" 답글 미리보기 박스 2개(별도 게시물 아님, 인용/댓글), 그 아래
   같은 글쓴이의 "관련 링크" 한 줄(다른 제목의 다른 글로 이어지는 링크 — 이것이 별도
   게시물로 잡혀야 하는지 애매함).
4. **365mc.com 공식 사이트 모듈** — 출처가 "365mc.com · www.365mc.com › intro"처럼
   URL 경로로 표시됨(카페/블로그와 다른 헤더 형식). 본문 아래 "HOME - 스페셜람스 - ..."
   같은 브레드크럼 경로의 2번째 하위 링크, "관련문서 더보기 >" 버튼.
5. **네이버 지식iN 모듈** — 헤더가 "네이버 지식iN"(작성자 이름이 아님), "Q. ..." 질문
   제목, 답변자 프로필(의사/온라인콘텐츠창작자 배지 + 이름 + 날짜)이 박스 안에 별도로 있음.
6. **"함께 많이 찾는" 연관검색어 칩 목록** — 게시물이 전혀 아님, 검색어 텍스트 5개
   (돋보기 아이콘과 함께 나열). 완전히 무시되어야 함.
7. 이후 다시 일반 블로그 글이 몇 건 이어짐.

## OCR 평가 시 유의사항 (정답 작성자 메모)

1. 블로그탭(이미지 1, 4)은 채널명 헤더 → 파란 제목(1~2줄) → 회색 본문 → 다음 헤더까지,
   구조가 균일해서 `segmentation.ts`의 줄-간격 기반 클러스터링이 원래 겨냥한 케이스와
   거의 일치한다. 정확도가 상대적으로 높게 나올 것으로 예상된다.
2. 통합탭(이미지 2, 3)은 카페의 "RE" 답글 박스, 공식 사이트의 글머리 기호 목록과
   브레드크럼 하위 링크, 지식iN의 답변자 프로필 박스, "함께 많이 찾는" 칩 목록처럼
   앱이 원래 가정한 "헤더 → 제목 → 본문" 3단 구조에 들어맞지 않는 레이아웃이 섞여
   있다. 순수 줄-간격 클러스터링은 이런 구조를 개별 게시물로 착각하거나
   (예: RE 답글 박스를 새 게시물로 오인) 반대로 합쳐버릴 가능성이 높다 — 이는 추측이
   아니라 실행 후 실제 결과로 확인한다.
3. 채널명 중 극단적으로 장식적인 경우("ღ MARYWORLD ღ", "ᅲ.° ★ ♡·÷", "-`,｡ ♡ ｡`'-")가
   여러 건 있어 스펙 18절 1번 항목("장식기호 섞인 채널명")을 실제 데이터로 검증하기
   좋은 케이스다.
4. 실제 캡처 해상도가 낮다(가로 ~400px, 세로 3000px 이상의 매우 좁고 긴 이미지) —
   합성 테스트에서 쓰던 고해상도 이미지보다 실제 조건에 가깝고 더 도전적이다.
